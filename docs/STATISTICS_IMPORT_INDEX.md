# 收听统计导入匹配索引

## 背景

统计备份允许最多 20,000 个条目，音乐库性能门禁已经覆盖 10,000 首歌曲。原实现对每个没有精确媒体 ID 命中的条目执行一次完整 `songs.filter`，并在每次比较时重新规范化标题、艺术家和专辑。

在上限组合下，这会产生约：

```text
20,000 × 10,000 = 200,000,000
```

次身份比较。匹配已经在 `Dispatchers.Default` 执行，因此不会直接阻塞主线程，但仍可能长时间占用 CPU、增加内存分配并延迟导入预览。

## 新索引

`PlaybackStatisticsSongIndex` 在一次导入预览内构建一次，预先规范化每首歌曲的：

- 标题；
- 艺术家；
- 专辑；
- 时长；
- 媒体 ID。

索引包含：

```text
mediaId
title
title + artist
title + album
title + artist + album
```

每个备份条目根据自己实际拥有的字段选择最窄的候选桶，再应用原有的 3 秒时长容差。找到第二个候选后立即返回“歧义”，不再收集完整候选列表。

复杂度从“每个条目扫描完整音乐库”改为：

```text
建索引：O(歌曲数)
匹配：O(条目数 + 各身份桶内的真实冲突数)
```

最坏情况下，大量歌曲具有完全相同的可移植身份时仍需检查对应冲突桶；这是为了保持“多个候选必须跳过”的安全语义，不能任意选择第一项。

## 保持不变的安全语义

本次只优化候选检索，不改变导入协议：

- 精确媒体 ID 仍必须通过可移植身份确认。
- ID 冲突后仍回退到标题、艺术家、专辑和时长。
- 标题、艺术家和专辑仍忽略大小写、首尾空白与连续空白差异。
- 备份缺少艺术家或专辑时，不会要求歌曲对应字段为空。
- 导入时长和歌曲时长都已知时继续使用 ±3 秒容差。
- 歌曲时长未知时仍保留为潜在候选，因此可能产生歧义。
- 多个候选继续跳过并显示警告。
- 不可用条目、重复目标和幂等合并规则不变。
- 匹配预览完成前不写入 DataStore。

## 回归

新增 `PlaybackStatisticsImportIndexTest`：

1. 10,000 个可移植备份条目匹配 10,000 首歌曲，不设置不稳定的墙钟时间阈值。
2. 大小写和空白规范化保持一致。
3. 同身份歌曲通过时长容差唯一收敛。
4. 未知歌曲时长继续保留为候选，确保不会因优化而错误绑定。

完整 Android 构建、API 35 托管设备和性能工作流仍以对应提交的 GitHub Actions 结果为准。本测试证明功能规模与确定性，不等同于目标手机上的耗时、PSS 或热状态性能门槛。
